# 042 项目资产回收站设计（已批准）

2026-09-26。对应 PS-06 的删除与恢复片。用户选择“先放回收站，可恢复”，并明确同意按本设计实现。WorkBuddy 5.6.2 实机只读观察到资产右键菜单的“删除”，**未执行删除**；该产品是否采用回收站仍未验证。本合同规定熊宝自己的安全语义，不把推测写成对标事实。依赖已交付的 023A 私有资产、026 版本历史和 027 PDF 历史预览；任务引用、移动/重命名、硬配额与永久清理另立任务。

## 用户行为与边界

- 文件或文件夹菜单的“删除”先弹二次确认，文案明确“移入回收站，之后可恢复”；确认成功后该项及其当前可见子项从普通目录、搜索和预览消失。上传可复用被删项原来的名称。失败时保留原行并显示可重试错误。
- 资产页提供“回收站”入口，只列独立的回收根，显示名称、类型、原位置、删除时间和删除人；可单项恢复。第一片没有“永久删除”“清空回收站”或自动到期。项目本身被永久删除时，现有项目级删除规则仍生效；回收站不是项目级备份。
- owner/admin 可删除、恢复本项目任何普通资产；member 仅可删除自己创建的文件或整棵子树均由自己创建的文件夹，且仅可恢复自己删除的回收根。`created_by`/`deleted_by` 已失效或为空时，仅 owner/admin 可管理。隐藏根不可删除。当前项目成员均可列回收根，具体恢复按钮按服务端权限显示；非成员、撤权用户和跨项目 ID 一律 404。项目归档后可只读查看回收站，但删除、恢复返回 403。
- 不把逻辑删除等同于释放磁盘。现有 `/assets/usage` 继续报告**可见**文件的当前版本数量和字节；同一响应增加回收站当前版本数量和字节，前端分开标注“可见文件”和“回收站保留”。历史版本占用及真实配额不在这两个统计内，页面不显示凭空计算的剩余可用空间。用户当前 WorkBuddy 页面显示 10 GB 是账号快照，不用作熊宝硬编码额度。

## 数据与并发合同

配对的 SQLite/PostgreSQL v29 迁移在 `project_asset_nodes` 增加 `deleted_at`、`deleted_by`、`trash_root_id`、`original_name_key` 四个可空字段，并增加按项目查回收根、按回收根遍历的索引。迁移对现存节点保留活动状态。不可变 `project_asset_versions` 行和私有对象字节都保留；受限对象清理器不得把回收版本视作孤儿。

删除在一笔事务内先锁成员、核对项目非归档及目标/整棵可见子树的权限，再标记目标和所有**当前活动**后代：相同 `deleted_at`、`deleted_by` 和 `trash_root_id=目标 node_id`。目标的 `original_name_key` 保存原冲突键，`name_key` 临时改为 `U+001F + node_id`，释放同父目录原名；合法用户名称禁止控制字符，因此临时键不可由上传或建文件夹构造。后代保留原 `name_key`；已在回收站中的独立子项保持自己的回收根与删除元数据。删除目标若已删除或其父已删除，返回统一 404。SQLite `BEGIN IMMEDIATE`、PostgreSQL 成员锁加行锁维持成员撤权、并发上传/删除/恢复一致；锁序沿用 023A。

恢复也在一笔事务内先重验成员/角色/项目状态，再要求目标是 `trash_root_id=node_id` 的回收根、原父目录仍活动，且原父下没有同 `original_name_key` 的活动项；否则返回 409 且整棵子树保持回收状态。随后只复原与该 `trash_root_id` 相同的节点，根的 `name_key` 恢复为原键，四个删除字段清空。之前单独回收的子项仍在回收站。恢复后原 `node_id`、版本 ID、当前版和历史字节不变。数据库唯一约束是并发同名上传/恢复的最后防线；冲突映射为同一 409。重复删除返回 404，重复恢复返回 404，不返回已恢复对象的存在信息。

## 服务端与 UI 接口

`DELETE /api/projects/{project_id}/assets/{node_id}` 成功返回 204，仅表示原子移入回收站；`GET /api/projects/{project_id}/assets/trash?limit=&offset=` 返回按删除时间和 node ID 稳定排序的回收根分页；`POST /api/projects/{project_id}/assets/trash/{node_id}/restore` 成功返回安全节点元数据。错误沿用现有封套：非成员/未知/已删/跨项目 404，归档或有身份但无管理权限 403，名称或父目录冲突 409；中英服务端与前端错误键成对补齐。

所有既有普通读写入口都要拒绝已删节点和已删父目录：目录列表/搜索、父目录导航、当前与历史版本列表/下载、上传新版本、恢复旧版本、上传或新建到父目录、PDF 预览取流。普通列表和可见使用量按活动节点过滤，且过滤在数据库分页/聚合之前完成。未来“添加到任务”和产物回存必须另行重验活动状态，不能因为持有旧 node ID 获得回收字节。回收列表不返回 `object_key`、私有路径或成员不可见的机密信息；回收项本身不能下载或预览。

前端延用项目资产表格与抽屉/弹窗样式，提供删除确认、回收根分页和恢复；每次请求由当前 project ID 及递增请求序号约束，切项目或撤权立即清空旧行与回收数据。恢复后刷新原目录、回收列表和两类用量；同名 409 提示用户改名或处理冲突，但本片尚无移动/重命名功能，因此只能先保留回收项、待后续能力开放。资产二次确认、恢复、失败与无权限态都要在 1273×634 和窄窗口检查，不以仅显示菜单作为验收。

## 实施切片与验收

先提交失败测试，再由已配置的实现路由分别负责 v29/仓储/服务端和前端；GLM-5.3 只读审查固定 SHA，Codex 独立验收与整合。后端至少覆盖：旧库升级、SQLite 新库、PostgreSQL 迁移语义、文件及含嵌套回收项的目录、同名重建与恢复 409、两个并发恢复、撤权与归档、跨项目/隐藏根、所有历史下载与版本入口的已删拒绝、对象清理器保留回收字节、恢复后字节 SHA 一致。前端覆盖确认/取消、失败不消行、跨项目晚到响应、同名恢复冲突和中英文文案。再用隔离账号做 owner/member/撤权用户浏览器旅程，核对真实下载/恢复及本项目视觉；PostgreSQL 实库与 WorkBuddy 删除确认若未实际跑过必须标未验证。PS-06 在任务引用、Office 等预览、配额和视觉旅程齐备前保持开放。
