# 029 · 项目专家选择与新任务门禁合同

状态：GLM 设计只读审查有条件 GO；Codex 核对当前 `main` 已含 026 迁移、全局共享 Agent ACL、028 归档门禁和 Agent 删除路径，并修订其 P1/P2 后冻结实施。本批只覆盖 PS-07 项目级专家配置的一片，不代表技能、连接器、定时任务、专家团或 WorkBuddy 项目空间已完整对齐。

## 依据与产品选择

WorkBuddy 实机项目右栏有“管理专家”，弹窗显示已添加数量、专家卡片、“添加”和“取消/确定”；[官方 5.0.0 更新日志](https://www.workbuddy.cn/docs/workbuddy/Changelog)确认项目级专家配置按角色管理。只读观察未证明专家选择是否自动授权给项目成员。熊宝采用保守的第一片：owner/admin 只能把**已全局共享且启用的单专家**选入项目；这份项目名单不是 Agent 授权或工具凭据，成员创建任务时仍通过自己的既有 Agent ACL。项目不会因选中专家而分享任何个人 OAuth、Agent 私有工作目录或历史。

两种较小方案均不足以满足此片：只显示项目专家卡片不改变新任务行为，会形成假配置；选中专家即自动让所有成员使用私有 Agent，会越过既有 `require_agent_row` 与个人资源边界。因此本合同让非空名单成为**新项目任务**的候选门禁，并在服务端同事务验证；空名单保留 028 已有“从本人可用专家中选择”行为，避免升级旧项目后无法新建任务。界面明确说明空名单的默认行为。手动关联既有任务不受此名单影响。

## 用户可见结果

- 项目成员可在右栏看见当前已选专家和不可用占位；owner/admin 打开“管理专家”双栏弹窗，左侧已添加列表、右侧可添加的共享单专家卡片，支持搜索、添加、移除、调整顺序、取消和保存。只有服务端确认保存后才更新项目页；刷新和其他成员重新进入得到相同顺序。成员只读，非成员无法读到名单。UI 使用熊宝品牌组件和中英文文案，在 1280×768 与约 800×728 视窗不遮挡项目操作。
- 名单非空时，项目“新建项目任务”选择器只展示其中当前仍共享、启用、运行中且本人可用的单专家；**即使选中专家的创建者本人把它取消共享，项目模式也不再允许新建任务**。名单为空时保留 028 的现有可用单专家选择。名单或选中专家状态变化时显示“配置已变更/专家不可用”，刷新后重新选择并确认项目指令；绝不创建看似成功的假任务。修订号仅是请求协议字段，不作为用户可见文案。
- 旧项目任务保留创建时固定的 `agent_id` 和 028 项目指令快照，名单之后的修改不替换专家、不改变旧任务私密 ACL。正在运行中的旧任务继续受既有 Agent ACL、任务 owner 与项目成员检查。仅凭本片不声称 Agent 自身 system prompt、技能或连接器配置已被复制成不可变快照。

## 服务端合同

- 成对 027 迁移：`project_spaces.experts_revision INTEGER NOT NULL DEFAULT 0`，`project_experts(project_id, agent_id, sort_order, added_by, added_at)`，`(project_id, agent_id)` 唯一；`project_id` 外键指向项目公开字符串 ID 并级联删除，`agent_id` 外键指向 `agents.agent_id` 公开字符串唯一列并在专家硬删除时级联清理，`added_by` 可空且指向 `users.id`、删除用户时设为 NULL；给 `project_task_contexts` 增加 `expert_selection_revision INTEGER NOT NULL DEFAULT 0`。旧项目没有行且修订号为 0，保持原有创建行为。当前用户仓库 `main` 已含 026，迁移必须同时覆盖 SQLite 和 PostgreSQL，不重用旧版本。修订号只记录**管理员通过 PUT 保存名单的配置版本**；取消共享/停用或 Agent 硬删除改变有效可用集却不增加修订号，GET 必须始终实时重读并将不可用资料置空，POST 必须重新校验当前列表与 Agent。任务 context 的修订号是创建时的配置版本审计值，不代表当时所有 Agent 生命周期状态的版本。
- `GET /api/projects/{id}/experts` 仅成员可见，响应 `{revision, items:[{agent_id, name|null, description|null, status}]}`，按 `sort_order` 稳定排序；已停用或取消共享的专家返回 `name=null, description=null, status='unavailable'` 的占位，硬删除后由外键移除，不泄漏其当前私有资料。未知项目/非成员同形 404，归档项目遵循其他项目详情的只读策略。读取时的名单和 Agent 状态来自当前数据库，不能仅因修订号相同而复用旧缓存。
- `PUT /api/projects/{id}/experts` 仅 owner/admin；请求 `{expected_revision, agent_ids}`，最多 20 个、无重复。服务端在同一写事务内按“成员行 → 项目行 → Agent 行（ID 排序）”顺序复核角色、未归档状态、修订号和每个 Agent 的 `kind='expert'`、`enabled=1`、`is_shared=1`；PostgreSQL 分别以成员 `FOR SHARE`、项目 `FOR UPDATE`、目标 Agent `FOR SHARE` 锁行，SQLite 使用现有写事务。不接受私有专家或专家团。修订号冲突返回 409 且不改变名单；完全相同的有序名单保持修订号不变；真实变更一次性替换并加 1。项目动态仅记操作者、时间和新数量，不写 system prompt、个人凭据或私有 Agent 资料。
- `POST /api/projects/{id}/tasks` 在 028 请求中新增可选的 `expected_experts_revision`（非负整数）。新前端必须发送；028 旧客户端缺省时，**空名单保留旧行为，非空名单返回 409 `PROJECT_EXPERTS_CHANGED`**，不能绕过配置。服务端按成员 `FOR SHARE` → 项目 `FOR SHARE` → 目标 Agent `FOR SHARE`（PostgreSQL；SQLite 仍为写事务）锁序，在任何 thread/link/context 插入前检查未归档状态和当前修订号；不符返回 409 且无任务。名单非空时只接受名单里**仍然 `is_shared=1`** 的 Agent，包含其创建者本人；名单为空时走 028 既有 Agent ACL。无论名单如何，始终重新验证 Agent 当前 ACL、持久启用状态和类型，项目名单绝不作为授权；路由在写入前另查运行中的 Agent。成员已获项目访问但选中专家失效时返回统一的 `PROJECT_EXPERT_UNAVAILABLE`，前端刷新名单并显示可恢复错误，不公开 Agent 私有资料。运行中的 Agent 若在事务提交后停止，已创建的私密对话仍在，首次执行明确显示不可用，不虚构模型执行成功。创建时把实际修订号写入 context 行以供审计；任务快照仍只含项目指令，不复制 Agent 的个人配置。并发移除项目成员、取消 Agent 共享或修改名单时，要么按旧配置完整创建、要么拒绝且无半条任务。
- 本批不在全局 Agent 路由上新增项目成员特权，不改个人连接器、工具、文件、聊天历史和 WebSocket 的现有授权。项目配置切换不会给既有私密任务的其他成员正文权限，也不会让专家团 peer 继承项目指令。

## 前端与状态

- 新 API 使用独立类型化模块；项目详情从服务端读名单和修订号。保存冲突刷新真实名单，保留用户草稿并提示重新确认；取消直接丢弃草稿。切项目、撤权或关闭弹窗使晚到响应失效，避免旧项目名单显示到新项目。保存中禁止重复提交和遮罩关闭。
- 任务创建弹窗同时预览当前项目指令摘要和项目专家修订号；409 无论来自指令还是专家名单都要求刷新项目详情、清除确认并重新选择，不能自动重试。若名单里的专家后来不可用，明确禁用该项并提示管理员调整。创建成功仍只是进入私密对话，不自动发送首轮消息。
- 右栏其他“连接器、技能、定时任务”继续标未开放；专家配置的新可操作入口不能使这些卡片误显示为已启用。

## RED→GREEN 与验收

1. 后端先写新库/026 升级迁移、owner/admin/member/outsider 权限、角色变化、归档、重复/上限、空/非空门禁、028 旧客户端缺省修订号、共享撤销/停用/硬删除、旧修订 409 无副作用、并发保存/创建、排序变更持久化且加 1、context 审计修订号、旧任务不受名单修改影响的失败测试；对 GET 增加专家取消共享/停用后 `name` 和 `description` 均为 null 的隐私断言，再实现最小逻辑。SQLite 双连接交错与 PostgreSQL 实库分别验证，若本机没有 PG 则明确标未实测。
2. 前端先写列表/保存/取消/冲突/切项目/撤权/晚到响应/窄屏与任务选择器的行为测试；再接真实 API。无可选专家、只有专家团、只有已取消共享专家、提交中关闭等状态可被用户理解且不会产生假成功。中英文词条、键盘焦点和加载/失败态覆盖。
3. Codex 独立检查白名单 diff、定向及相邻测试、Ruff/mypy/TypeScript/ESLint/Prettier/构建、三身份隔离 HTTP 与真实登录浏览器；固定提交交 GLM 只读审查，修复阻断项后及时推送并核对用户仓库远端 SHA。
4. 未做真实模型调用、Windows 安装包、PostgreSQL 实库或 WorkBuddy 逐状态视觉时分别保留差距，不能核销 PS-07 或 25 项总矩阵。
